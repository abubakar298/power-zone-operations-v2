# Encrypted application backups

Administrator → Team access → Encrypted database backups. Enter the current administrator password and a separate encryption passphrase of 16–128 characters, confirm it, then confirm Download encrypted backup. Save the `.pzb` file and copy it to an external disk. Keep the passphrase separately from the disk. The app clears these fields after preparation; neither passphrase is stored in the database or audit log. Prepared-download history does not prove the file was saved or copied. Downloads are manual, not an automatic daily service.

The archive contains a transactionally consistent snapshot of all public application tables: customers, sites, rates/specifications/rules, user accounts/password hashes, surveys/uploads, BOQs/costings, quotes and revisions, approvals, PO/IPO data/uploads, Peachtree snapshots, Operations/department data, audit history and any historical test recovery archive. Row JSON is passed to PostgreSQL without JavaScript numeric conversion on restore. Live sessions, throttling counters, account links and outbound email queue contents are deliberately omitted to prevent replay or accidental re-sending. Hosting configuration, application source, email/API credentials and infrastructure secrets are not database records and are not restored from this file.

The file uses AES-256-GCM authenticated encryption with a fresh random salt/nonce and scrypt key derivation, with compressed records inside. Wrong passphrases and modified files fail authentication. Passphrase loss is unrecoverable. Downloads require current Admin role, recent password confirmation, same-origin and CSRF checks, and a persisted limit of three attempts per 15 minutes. Preparation is recorded in audit history. One export at a time is allowed; raw row data is compressed/encrypted as a stream to a temporary private file, which is deleted after the response. Current archive limit is 512 MiB of uncompressed row data; larger deployments need a standard PostgreSQL backup process. The format is an application recovery archive, not a native pg_dump file.

## Operator restoration

Restore using the repository release matching the archive's migration checksums. Have the owner enter the backup passphrase securely; never paste it in chat, commit it, log it or put it in command arguments. Run `pnpm exec tsx scripts/restore-backup.ts /secure/path/archive.pzb` with `PZ_BACKUP_PASSPHRASE`, `PZ_RESTORE_DATABASE_URL`, and `PZ_RESTORE_CONFIRM_EMPTY=restore-to-separate-empty-database` securely set in the operator's environment. Set `PZ_RESTORE_TLS=true` for external connections and use trusted certificates. Do not use the production DATABASE_URL variable or production database as the target. A restore is refused if any public table already exists in the target. The operator must use an isolated database with no users connected.

The tool authenticates/decrypts the file, checks matching migrations, initializes a new schema, loads records in a transaction with foreign keys deferred, verifies constraints, restores sequence positions and returns the backup timestamp/table count. It never disables immutable document triggers. No restore HTTP endpoint exists. A failed data load rolls back restored rows; schema migrations may already have initialized the disposable target, so retry with a new empty target. Do not delete production data to make it empty.

Before cutover, verify customer/site/document counts, recent versions, approval history, uploaded file bytes/hashes and financial totals, then start the app against the recovered database with outbound email disabled. Existing passwords remain usable; all users sign in again. Set the recovered database connection only after verification and keep the original database for rollback. Test monthly and after material schema changes. Manual downloads supplement managed database recovery; they do not remove free database expiry or protect records entered since the last download.

Validation includes an encrypted full sample dataset round trip through a fresh native PostgreSQL database, restored IPO snapshots and upload bytes, restored administrator login, non-reusable old sessions, identity sequence positions, role/CSRF/password checks, damaged archives and non-empty target refusal. Production data has not been restored or deleted for this test.
